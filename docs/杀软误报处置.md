# 杀软误报处置（Windows Defender）

> 事故记录：**v1.0.16（2026-09-14 发布）安装后无法打开**。
> 用户反馈「在下载页装了 1.0.16，双击没反应」，1.0.15 正常。
> 排查结论：**不是程序缺陷，是 Windows Defender 的机器学习模型把未签名主程序误判成木马并隔离**。

## 1. 现象与判定依据

用户看到的弹窗：

```
C:\Users\<用户>\AppData\Local\Mindmate\mindmate.exe
无法成功完成操作，因为文件包含病毒或潜在的垃圾软件。
```

本机（Windows 11 + Defender 定义 1.459.209.0）实测：

| 检查项 | 结果 |
| --- | --- |
| 安装包 `Mindmate_1.0.16_x64-setup.exe` 本身 | 未被检出（能正常安装） |
| 安装包内的主程序 `mindmate.exe` | 复制到任意目录后数秒内被隔离 |
| 检出名 | `Trojan:Win32/Bearfoos.A!ml`（`!ml` = 机器学习启发式判定，高严重度） |
| 处置动作 | `CleaningActionID 2` = 隔离（文件被删除） |
| 触发时机 | **安装/落盘即触发**，与是否运行无关 |
| 同一提交、本机自行构建的同版本 exe | **未被检出** |
| 1.0.15 安装包 | 未被检出 |

关键证据：同一份源码、同一个版本号，本机构建的产物判定为干净，CI 构建的产物被判定为威胁。
两者的 `VERSIONINFO`、导入表、节表结构一致，只是**字节不同**（编译时常量/元数据差异）。
机器学习模型是按字节特征打分的，说明这是**误报**，不是程序真的有问题：

- 程序不做任何可疑行为：不注入、不提权、不加密文件、不连外网（除用户自行配置的 AI 接口）。
- 主程序只有两件"像恶意软件"的行为：**写注册表 Run 键**（用户显式开启开机自启时）和
  **监听本机端口**（前端页面与 API 走 `127.0.0.1`）。这两点对"带持久化的无签名网络程序"来说是
  典型的启发式高危组合，再叠加 `strip = true` + `lto = true` 的发布配置（符号表被剥离，
  看起来像加壳程序），模型很容易给出高分。

## 2. 已落地的修复（发布流程侧）

误报本身我们无法从代码里"修掉"——能修的是**发现它的能力**：

1. **`scripts/defender_check.py`**：发布前用本机 Defender 扫即将发布的二进制。
   - 必须先把文件复制到 `%TEMP%` 下的中立目录再扫：项目目录/安装目录通常已在 Defender
     排除项里，而 `MpCmdRun` 尊重排除项——原地扫描恒为"干净"，等于没扫。
   - 判据：复制后文件是否被实时保护清掉 + `MpCmdRun -Scan -ScanType 3` 退出码（2 = 检出）。
   - 用于 CI：`--strict` 检出即失败；本地自查默认只告警。
2. **CI 拦截**：`.github/workflows/release.yml` 的 Windows 构建在**上传产物前**执行
   `python scripts/defender_check.py --strict ...`。被误报的平台当日构建直接失败，
   不会再发出"装完打不开"的包。
3. **全量验收纳入**：`scripts/run_all_tests.py` 增加「杀软误报自检（Windows Defender）」一项，
   本地发布前跑一次即可覆盖。
4. **下载页说明**：`scripts/make-manifest.mjs` 生成的 Windows 分组下增加自救指引
   （见"保护历史记录 → 排除项 → 重装"），并保留 SHA-256 供用户核对完整性。
5. **静态守卫**：`scripts/desktop_test.py` 断言自检脚本、CI 步骤、下载页说明、文档都在位。

## 3. 遇到误报时的处置顺序

```bash
# 1) 先确认是不是误报（同一二进制反复扫，观察是否稳定检出）
python scripts/defender_check.py src-tauri/target/release/mindmate.exe
python scripts/defender_check.py src-tauri/target/release/bundle/nsis/*.exe

# 2) 若确认误报：改版本号重新构建，再扫一次
#    机器学习判定边界对字节级改动敏感，"微调 + 重扫"经常直接通过。
#    已验证可用的一次改动：调整 release profile（例如 strip = false）或版本号。
npm run desktop:build

# 3) 仍被检出：向微软提交误报（本地定义更新后一般 24–72 小时有结论）
#    提交地址 https://www.microsoft.com/en-us/wdsi/filesubmission
#    "Do you believe this file is incorrectly detected?" → Software developer → 上传文件

# 4) 用户侧应急（发出去之前已经误报在用户机器上时）
#    Windows 安全中心 → 病毒和威胁防护 → 保护历史记录 → 找到被隔离的 mindmate.exe → 允许
#    或：病毒和威胁防护 → 管理设置 → 排除项 → 添加文件夹 %LOCALAPPDATA%\Mindmate → 重新安装
```

## 4. 提交给微软的误报说明（可直接复制）

```
Detection name: Trojan:Win32/Bearfoos.A!ml
File: Mindmate_<版本>_x64-setup.exe (payload: mindmate.exe)

This is a false positive on an unsigned desktop application developed by us.

Product: Mindmate (智伴) — a local-first personal note/todo/reminder app.
Publisher: individual developer, no code-signing certificate yet.
Homepage / releases: https://mindmate-10v.pages.dev/
Source code: <公开仓库地址>

Why it is a false positive:
1. The flagged file is our own Tauri 2 desktop binary, built by GitHub Actions
   from the tagged source in the repository above (workflow: .github/workflows/release.yml).
2. The same source produces both a flagged and a non-flagged binary depending on
   build metadata bytes, and every version is reproducible from the public tag.
3. The application's only privileged behaviours are:
   - writing HKCU\Software\Microsoft\Windows\CurrentVersion\Run\Mindmate,
     and only when the user explicitly enables "start with Windows" in Settings;
   - listening on 127.0.0.1:<random high port> to serve its own UI and local API
     to the bundled WebView. It makes no outbound connection except to the AI
     provider endpoint the user configures.
4. It does not inject into other processes, does not request elevation, does not
   encrypt or modify user documents, and does not self-update from untrusted sources
   (updates are minisign-signed; the public key is pinned in the app config).
5. SHA-256 of the installer: <SHA-256>
   The installer is not flagged; only the extracted main executable is.

Request: remove the machine-learning detection for this binary and whitelist our
publisher so future releases are not flagged.
```

> 每次发版把 `<版本>`、`<SHA-256>`、`<公开仓库地址>` 换成当次值即可。
> 注意：WDSI 是按文件哈希受理的，**每个版本都要单独提交**；长期解法只有代码签名。

## 5. 长期方案：代码签名

| 方案 | 成本 | 效果 | 门槛 |
| --- | --- | --- | --- |
| OV 代码签名证书（DigiCert / Sectigo 等） | ¥1500–3000/年 | 消除绝大多数"未知发布者"告警与 ML 误报；**SmartScreen 信誉仍需累积** | 需企业/个体工商户主体资质 |
| EV 证书（含 USB 硬件令牌或云签名） | ¥3000–6000/年 | 立即获得 SmartScreen 信誉，误报率最低 | 资质审核更严 |
| Azure Trusted Signing | 约 $9.99/月 | 微软自家短时效签名，对 Defender 误报最友好 | 需通过身份验证（个人可申请，视地区而定） |
| 不签名（当前） | 0 | 依赖本仓库的自检拦截 + 用户手动排除 | — |

接上签名后，需要同步改三处：

1. `.github/workflows/release.yml`：Windows 构建步骤注入证书（Tauri 会读取
   `TAURI_WINDOWS_CERTIFICATE` / `TAURI_WINDOWS_CERTIFICATE_PASSWORD`，
   或在 `bundle.windows` 下配置 `certificateThumbprint` / `digestAlgorithm` / `timestampUrl`）。
2. 证书与口令只放 GitHub Secrets，**绝不入库**（`.gitignore` 已排除 `*.pfx` / `*.p12` / `secrets/`）。
3. 下载页与本文档移除"未签名"说明段落。

## 6. 这次事故暴露的流程缺口（已补齐）

| 缺口 | 现在怎么防 |
| --- | --- |
| 发布流水线从不真正运行一次杀毒扫描 | CI 在 Windows 产物上传前强制 `--strict` 扫描 |
| 只在本地构建过、从未验证「用户装完能不能打开」 | 自检脚本 + `run_all_tests.py` 纳入；发布后下载回发布物再扫一次 |
| 用户看到"打不开"没有任何自救信息 | 下载页 Windows 分组给出排查与排除项指引 |
| 同类问题只能靠用户反馈发现 | `desktop_test.py` 静态守卫确保上述机制不会在后续提交里被删掉 |
