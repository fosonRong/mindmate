## 1. 目标与范围

### 1.1 为什么分两期

| 期 | 目标 | 关键动作 | 商业含义 |
| --- | --- | --- | --- |
| **第一期** | **把一个"免费、完整、好用"的产品交到用户手里** | 全功能免费开放 + 中英日韩四语 + **免登录** + 自配模型引导 + **零成本发布与自动更新** | 先获客、先验证价值与口碑；不引入任何付费门槛，也不引入服务器成本 |
| **第二期** | **把免费用户转化为付费用户** | 注册登录（手机号/微信/邮箱）+ 设备绑定（一机一码）+ 30 天试用 + 订阅与兑换码 | 开始收费；服务端引入（账号与授权），成本可控 |

**这样排的好处**：第一期零服务器、零资质、零成本即可上线（不需要域名备案、不需要短信资质、不需要企业主体），能最快拿到真实用户反馈；第二期再补商业化能力，且**第一期的四语与发布/更新通道可以直接复用**，不返工。

### 1.4 三条底线

| 项 | 结论 | 为什么 |
| --- | --- | --- |
| **零 AI 成本** | 用户自配 Key，模型费用由用户直接付给厂商 | 开发者不承担 token 成本 → 毛利接近 100%，第二期的 ¥198 终身版也不会变成负债 |

## 3. 商业模式与定价（**第二期上线**）

### 3.1 定价阶梯（已定）

| 方案 | 价格 | 折合 | 同时激活设备数（建议） | 定位 |
| --- | --- | --- | --- | --- |
| 试用 | 30 天全功能 | — | 1 台 | **完成手机号或邮箱验证即开始**；到期降 Free，**已录入数据不收回** |
| 月付 | **¥9.9 / 月** | ¥9.9/月 | 1 台 | 低门槛转化 |
| 年付 | **¥98 / 年** | ≈ ¥8.2/月（8.2 折） | 1 台 | **主推**（现金流最好） |
| 终身 | **¥198** | 约 2 年月付即回本 | 2 台 | 高意向用户一次收割；零 AI 成本 → 不会成为负债 |

### 3.2 免费版 / Pro 边界的**引入时机问题（重要）**

第一期已经把**全部功能免费**开放了。第二期要收费，就必须回答："凭什么把送出去的东西收回来？" 本方案的处理：

| 原则 | 做法 |
| --- | --- |
| **老用户不被收走功能（grandfather）· 已定 B 方案** | 第二期上线前已安装的第一期用户（老用户），**赠送 12 个月 Pro 权益**；只对"新用户"或"新增能力"收费。判定与实现见 3.2.1 |
| 卖"新增价值"而非"回收旧价值" | 第二期新增的能力作为 Pro：**多端同步、设备名额（第二台设备）、优先支持、大版本更新**；同时把第一期已免费的推送/归档/模板**继续免费** |
| 若确实需要收费项 | 至少保证：**已录入数据永远可导出、记录/待办/提醒永久免费**（数据不被锁） |

#### 3.2.1 B 方案（老用户送 12 个月 Pro）的落地规则

| 项 | 规则 |
| --- | --- |
| **老用户定义** | 首次安装/首次运行时间 **早于商业化上线时间（cutoff）** 的用户。cutoff 取第二期正式发版的时间点，在服务端配置（可远程调整） |
| **如何取证** | 第一期（免登录）阶段就在客户端埋下三处互相印证的"最早使用证据"：① 数据目录 `.first_seen` 文件（含首次运行时间 + 版本号 + HMAC）② 数据库最早一条记录（`nodes.created_at` / `settings.created_at`，由 Rust 直接读取，普通用户改不了）③ 本地 `settings` 表 `first_seen_at` |
| **上报时机** | 第二期用户**首次注册/登录**时，客户端把上述证据一并上报；服务端据此判定是否为老用户（三方取最早值） |
| **权益签发** | 判定为老用户 → 服务端签发 `plan = pro`、`source = grandfather`、`expires_at = 注册日 + 12 个月` 的权益；**从注册日起算**（不是安装日），更公平也更好实现 |
| **界面呈现** | 账号页显示「老用户福利 · Pro 权益至 2027-09-13」，并附一句"感谢早期支持" |
| **到期后** | 降为 Free，但**第一期已免费的能力（记录/待办/提醒/统计/AI/推送/归档/模板）继续免费**，只失去第二期新增能力（多设备、云同步、优先支持） |
| **滥用边界（务实说明）** | 用户删掉数据目录或重装系统后会失去老用户证据 → 按新用户走 30 天试用。这是可接受的（这是"送福利"而非"防线"）；服务端对大量相同 `first_seen` 值的上报做风控观察即可，不做拦截 |
| **不接受的反例** | 不要用"本地时间"单独判定（可改系统时间）；不要因为取证失败就判定为新用户而拒绝——**取证失败时给 12 个月 Pro 兜底**，宁滥勿缺（代价可控，口碑收益大） |

> 决策已定：**(B) 老用户送 12 个月 Pro**。备选口径 A（永久全免）收入最少但口碑最好，C（不做）差评风险高 —— 均不采用。

## 4. 模型配置引导（**第一期**）

### 4.1 目标

让完全不懂大模型的用户在 2 分钟内配好模型并看到「✅ 已连通」；配不好也能看懂"错在哪、怎么办"。

### 4.2 三步向导（升级现有设置页 AI 区 + 首启引导第 3 步）

```
① 选厂商            ② 领 Key                    ③ 粘贴并测试
┌────────────┐      ┌──────────────────────┐    ┌────────────────────────┐
│ DeepSeek   │      │ 点击「去申请 Key」→    │    │ Key: sk-••••••          │
│ 智谱 GLM   │  →   │ 打开厂商控制台（新窗口）│ →  │ 地址: 自动填入（可改）   │
│ Kimi       │      │ 复制 API Key          │    │ [ 测试连接 ] ✅ 已连通    │
│ 通义千问   │      │ 提示：新用户常有赠送   │    │ 模型：deepseek-chat      │
│ OpenAI     │      └──────────────────────┘    └────────────────────────┘
│ 本地 Ollama │
└────────────┘
```

| 环节 | 做法 | 现状 |
| --- | --- | --- |
| 厂商卡片 | 每个预设加「去申请 Key」外链 + 一句话成本提示（"写一份日报约几分钱"） | 新增 |
| 地址预填 / 协议识别 | 选中即填 base_url 与推荐模型；自动识别 OpenAI / Anthropic 兼容并提示 | ✅ 已有 |

## 5. 账号授权与一机一码（**第二期**）

### 5.1 登录方式与**前置资质门槛**

| 方式 | 体验 | 资质要求 | 成本 | 定位 |
| --- | --- | --- | --- | --- |
| **手机号 + 短信验证码** | 最好：输手机号收码即完成注册与登录，**无需记密码** | ⚠️ **需企业/个体主体**：短信服务商**签名 + 模板审核**（1–3 工作日） | ¥0.03–0.05/条 | **主推** |
| **微信扫码登录** | 桌面端很顺：扫码即登录 | ⚠️ **需企业主体**：微信开放平台「网站应用」认证 **¥300/年** | 0 | 辅推（有主体即做） |
| 邮箱验证码登录 | 尚可；无密码 | **无资质门槛**（复用现有 SMTP 或第三方免费额度） | ≈0 | **暂无主体时的兜底**，同时用于找回 |
| 密码登录 | 一般 | 无 | 0 | 不提供（省掉"忘记密码"支持成本，也天然免撞库） |

> ⚠️ **前置资质是第二期唯一的硬门槛**：手机号短信与微信扫码都要求主体资质。若暂无企业/个体主体，第二期先上「邮箱验证码登录」；主体就绪后**增量**加上手机号与微信 —— 账号模型不变，只新增绑定关系与登录入口，不返工。
>
> 三种方式共用同一套账号：**邮箱可独立完成注册、登录、找回**；手机号与微信是"更好用的入口"，不是唯一入口。任何一个入口被第三方政策卡住，都不会让已有用户登不进来。

### 5.2 手机号注册登录（主路径）

| 步骤 | 行为 |
| --- | --- |
| ① 输入手机号 | 客户端格式校验；服务端风控检查（同号 / 同 IP / 同设备频次） |
| ② 图形验证码 | `GET /v1/captcha` 取图形或滑块验证码 —— **防短信轰炸的第一道闸**（短信是要花钱的） |
| ③ 发送验证码 | 6 位数字、**5 分钟有效**、同号 **60s/次 + 10 条/天**、同 IP 20 条/天，超限熔断并告警 |
| ④ 校验即登录 | 通过后：账号不存在则**自动注册**，存在则直接登录；签发 JWT（access 2h + refresh 30d，refresh 轮转） |
| ⑤ 绑定设备 + 开始试用 | 自动注册当前设备（占一个名额）；**首次注册同时开始 30 天试用** |
| ⑥ 存储 | 手机号**加密存储 + 哈希唯一索引**；日志与审计**不落明文手机号** |

### 5.3 微信扫码登录（辅路径，桌面端体验最佳）

```
客户端                            服务端                            微信开放平台
  │  GET /v1/auth/wx/qrcode ────► 生成 state（32 字节随机，2 分钟过期）
  │  ◄── state + 授权 URL ───────┤
  │  展示二维码                    │
  │  每 2s 轮询 /wx/poll ────────► pending / scanned / confirmed
  │                               │  ◄── 回调 /wx/callback?code=&state=
  │                               │      校验签名 + code 换 openid/unionid
  │                               │      已绑定账号 → 签发 token
  │  ◄── confirmed + tokens ──────┤      未绑定 → 需补绑手机号
```

| 规则 | 说明 |
| --- | --- |
| 首次扫码需绑手机号 | 通过短信验证码绑定后才开始试用 —— 防止批量垃圾账号，也让账号可追溯、可找回 |
| 账号唯一性 | 以 **`wx_unionid`** 为准（同一用户在不同应用下 openid 不同、unionid 相同） |
| 会话安全 | `state` 随机 32 字节、一次性、2 分钟过期；微信回调**校签**且 `code` 只能用一次 |
| 浏览器端 | 微信内直接网页授权跳转（同一套服务端回调） |
| 解绑/换绑微信 | 客户端「账号 → 安全设置」提供（需短信验证，防止盗号后绑定） |

### 5.4 订阅与账号绑定（一机一码的落地口径）

| 概念 | 归属 | 说明 |
| --- | --- | --- |
| **套餐 / 到期时间 / 试用状态（entitlement）** | **账号** | 换机、重装、换平台都跟着账号走，**不随设备丢失** |
| **使用名额（device slot）** | 设备 | 设备只是"占一个名额"；试用/月/年 **1 台**、终身 **2 台**（待确认） |
| 解绑（换机） | 设备 | 客户端自助解绑（每月 1 次、冷却 30 天），超出走客服 |
| 数据 | **仍只在本机** | 换机不迁移数据（数据本就不在云上）；跨机迁移用已有的 JSON 导出/导入；云同步为后续可选 |
| 心跳 | 设备 | 启动时 + 每 24h 拉取权益；离线宽限 **7 天** |
| 名额已满 | 设备 | **拒绝激活新设备**并列出已绑定设备，引导先解绑（不做静默挤下线，避免投诉） |
| 设备指纹 | 设备 | `SHA-256(MachineGuid + 系统盘序列 + 用户名)`：不可逆、不含个人信息；换主板/系统盘会变 → 视为新设备 |

> 一句话概括：**订阅跟着人走，名额跟着机器走**。这就是一机一码的核心语义。

### 5.7 安全与反作弊

| 风险 | 对策 |
| --- | --- |
| **短信轰炸**（直接烧钱） | 图形验证码前置 + 同号 60s/次、10 条/天 + 同 IP 20 条/天 + 设备指纹限流 + **日消耗告警与自动熔断** |
| 验证码暴力破解 | 6 位数字 + 5 分钟有效 + 同码最多 5 次尝试即作废 + 同号失败锁定 |
| 扫码 `state` 重放 | 随机 32 字节、一次性、2 分钟过期 |
| 微信回调伪造 | 服务端校验微信签名 + `code` 一次性消费 |
| 撞库盗号 | **全程无密码**，天然无撞库面；提供"登录设备列表 + 异常登录提醒" |
| 兑换码泄漏/枚举 | 20 字符强随机（≈100 bit）+ 一次性核销 + 限流 + 失败封禁 |
| 一号多机 | 同时激活设备数上限 + 解绑冷却 + 心跳活跃度 + 风控标记 |
| 审计 | 登录、绑定、解绑、兑换、退款、封禁全留痕（保留 6 个月） |

### 5.8 隐私与合规（第二期必做）

| 项 | 要求 |
| --- | --- |

## 8. 自动更新（第一期打通）

### 8.1 技术方案

| 项 | 设计 |
| --- | --- |
| 插件 | `tauri-plugin-updater`（**当前未接入，需新增依赖与配置**） |
| 清单端点 | `https://<project>.pages.dev/latest.json`（静态文件，与业务完全解耦） |
| 清单格式 | Tauri v2 标准：`version / notes / pub_date / platforms["windows-x86_64"].{signature,url}` |
| 签名 | **Ed25519**：`tauri signer generate` 生成密钥对；公钥写 `tauri.conf.json` 的 `plugins.updater.pubkey`；私钥存 GitHub Secrets（`TAURI_SIGNING_PRIVATE_KEY`）+ 离线备份 |
| 校验 | 客户端下载后**验签**，签名不符 → 中止更新并提示（防中间人替换安装包） |
| 检查时机 | 启动后延迟 30 秒检查 + 每 24 小时一次；设置项可关（企业环境友好） |
| 下载策略 | 后台静默下载 → 提示"重启并更新"；用户可"稍后"；网络失败自动改为下次启动再试 |
| 更新安装 | Windows 上走 NSIS 静默安装（保留数据目录 `%APPDATA%\Mindmate`） |
| 数据安全 | 更新前**不触碰数据目录**；配合第 8.3 的迁移机制，保证版本升级不丢数据 |

### 8.2 ⚠️ 两个必须提前知道的限制

| 限制 | 说明与对策 |
| --- | --- |
| **Tauri updater 不支持"降级"** | 它只会把客户端升到清单里的更高版本。所以**回滚不能用"把清单指回旧版本"**，正确做法是：**发一个版本号更高、内容为回退代码的补丁版本**（例如 1.1.2 → 1.1.3 修复 1.1.2 引入的问题）。因此"发布前自测 + 灰度"比回滚更重要 |
| **清单被改了会不会被投毒？** | 清单里的 URL 与签名都由私钥签名，攻击者改了清单也过不了验签；所以**私钥只存 Actions Secrets + 离线备份，绝不入库**。万一私钥丢失，只能换密钥并让老客户端走一次"手动下载安装"（所以要备份） |

### 8.3 数据库迁移（**第一期必须做，自动更新的前置依赖**）

一旦开了自动更新，用户就会带着旧数据升级到新版本 —— 没有迁移机制就会丢数据。现状 `migrate()` 只有"建表"分支，必须扩展：

| 规则 | 说明 |
| --- | --- |
| 迁移链 | `[(2, "ALTER/CREATE …"), (3, "…")]` 按 `PRAGMA user_version` 逐级执行 |
| 事务 | 全部迁移在一个事务内；任一步失败整体回滚，版本号不前进 |
| **升级前自动备份** | 复制 `data.db` → `data.db.bak.v<旧版>`（保留最近 3 份），失败时提示一键恢复 |
| 只增不改 | 只加表/加列，不删列、不改列语义；需"改"用"新列 + 回填 + 读时兼容" |
| 幂等 | 可重复执行不报错（`IF NOT EXISTS` / 判空回填） |
| 高版本保护 | 库版本高于程序支持版本 → 拒绝写入并提示升级程序（防止用旧版损坏数据） |
| 终极退路 | 已有 JSON 导出/导入（导出→重装→导入） |

### 8.4 灰度与观测

| 项 | 做法 |
| --- | --- |
| 灰度（零服务端） | 客户端按**设备指纹哈希**决定读取 `stable.json` 还是 `canary.json`；把 canary 清单里的 URL 指向新版即可放量，比例写在客户端配置或清单字段里 |
| 放量节奏 | 10% → 50% → 100%，每档观察 24–48h |
| 观测方式 | 第一期无服务端 → 靠用户反馈 + 可选"匿名更新结果上报"（默认关闭）；第二期有服务端后可在清单里附带版本分布统计要求 |
| 失败兜底 | 更新失败不修改数据目录；用户仍可用旧版本；提供手动下载链接 |
